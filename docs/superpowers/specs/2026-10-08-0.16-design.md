# A 0.16: o pacote da 1.0, e o Servidor 1.0

> **Escopo.** A 0.16 é um pacote único. Ela leva tudo o que ia para a 0.15.2 e
> tudo o que estava planejado para a 1.0: o protocolo da 1.0, a nova versão do
> ponto de encontro, a sala pessoal, a API 6 de MODs com os três MODs oficiais
> portados, o web app do celular e o launcher por linha de servidor. Com ela
> nasce uma segunda numeração: a do **servidor**. O app 0.16 sai falando o
> **Servidor 1.0**.
>
> Este documento é o **spec-mestre**. Ele não substitui os specs de cada parte
> (o de 23/09 da sala pessoal e dos MODs na tela inteira, e o ADR 0057 do
> celular). Ele junta as partes, diz o que cada uma muda no fio, em que ordem
> elas entram e o que fica com o dono.

**Data:** 2026-10-08. **Estado:** rascunho, para revisão do dono.
**Base:** a `main` em `54f542f`, que é a v0.15.1 publicada (conferido pela API
de releases, como pede o `CLAUDE.md`).
**Fontes:** seis levantamentos por leitura do código, feitos em 08/10, um por
frente. As âncoras `arquivo:linha` abaixo são da `main` `54f542f`. As de
documentos antigos andaram, e cada uma foi conferida de novo.

## A frase que este documento implementa

*«Eu quero fazer um pacote todo e já lançar a 0.16 com todas as
atualizações, tanto da 0.15.2 quanto com os planejamentos da 0.16.»*

*«O SEELE funciona como um launcher. Ele precisa ter um histórico de versões
lançadas e permitir que o usuário consiga baixar versões anteriores, porque,
caso um mod não tenha sido portado, ele pode ter liberdade de voltar uma versão
do servidor para conseguir usar aquele mod.»*

*«A partir da 0.16 a gente vai ter as versões de servidores também. A gente vai
começar com a versão 1.0, que vai ser lançada com a 0.16.»*

## 1. Duas numerações: o app e o servidor

### O que cada uma é

**A versão do app** (0.16, 0.16.1, 0.17…) é o que o atualizador oferece. Ela
sobe sempre que o cliente muda.

**A versão do servidor** é o que o app e o `seeled` falam entre si: o
protocolo e a API de MODs.

- **Servidor 1.0** = protocolo da 1.0 + API de MODs 6. Sai com o app 0.16.
- **1.1, 1.2…** são acréscimos que não quebram: uma mensagem nova que o lado
  antigo ignora, ou uma API de MOD somada (a API 7, do `decorar`, seria
  Servidor 1.1).
- **2.0** é quebra: protocolo ou API de MODs incompatível. Começa uma linha nova.
- **Um conserto no `seeled` não muda a versão do servidor.** O `seeled` do app
  0.16.1 continua sendo Servidor 1.0.

A regra que torna isso verdade é o ADR «1.x nunca quebra o fio», que o Plano 3
já pedia (`docs/analise-para-a-1.0-2026-09-22.md:552`). **Ele passa a ser a
definição da versão de servidor.**

### Como «1.x» vira bytes (decisão D-fio-1)

Hoje o primeiro byte de todo quadro é o `PROTOCOL_VERSION`, que vale 8
(`crates/seele-proto/src/version.rs:124`).

**Recomendação:** o número que viaja continua um só e só cresce. O Servidor 1.0
é o protocolo 9, o 1.1 seria o 10, e assim por diante. Uma tabela congelada no
`seele-proto` diz a que linha cada número pertence (9 em diante é a linha 1).
O `Hello` passa a levar a faixa mínima–máxima que cada lado fala, e os dois
conversam pelo menor (o «carimbo negociado» do Plano 3).

Assim, «1.0» é o nome para pessoas e «9» é o que a máquina confere. O
`Unidade.protocol` do launcher (`crates/seele-lancador/src/manifesto.rs:88-94`)
continua significando o que diz, e a recusa de um servidor 0.15 (que manda 8)
já identifica a linha dele pelo primeiro byte. **Isso ainda precisa ser
medido.**

### O que o launcher faz com isso

- **Guarda o app mais novo de cada linha de servidor**, e não toda versão. A
  0.16.1 substitui a 0.16, porque as duas falam o Servidor 1.0.
- **Ao hospedar,** a pessoa escolhe a versão do servidor. O padrão é a mais
  nova. A tela diz quais APIs de MOD cada linha roda (a 0.15 roda 3, 4 e 5).
- **Ao entrar num servidor de outra linha,** o launcher abre o app mais novo
  daquela linha. Se ele não estiver no disco, o launcher baixa antes. A linha
  vem do link e, quando o link não diz, da recusa do servidor.
- **Cada linha tem os próprios dados** (`dados/servidor-0.15`, e não
  `dados/0.15.1`), para que um conserto da linha herde os dados dela. **A tela
  diz isso antes de abrir**: as conversas de uma linha não aparecem na outra.

### A linha legada: o Servidor 0.15

O app 0.15.1 aceita MODs das APIs 3, 4 e 5 (`crates/seele-proto/src/mods.rs:77`),
então essa linha roda todo MOD feito até hoje. Ela é a única que o launcher
oferece além da 1.0.

**A 0.15.1 já obedece a pasta de dados que o launcher passa.** O launcher põe
`SEELE_HOME` (`crates/seele-lancador/src/inicializacao.rs:51-60`), e no
`54f542f` o `config_dir` lê essa variável antes de qualquer outra coisa
(`apps/seele-app/src/main.rs:861-877`). Os argumentos `--hospedar` e `--entrar`
também já são lidos (`main.rs:284-297`).

**Dois problemas impedem de oferecer a 0.15.1 como ela está:**

1. **O botão de atualizar dela.** Aberta pelo launcher, a 0.15.1 tem o próprio
   botão. No Mac, o `tauri-plugin-updater` trocaria o `.app` do depósito pela
   0.16, porque ele move o `.app` atual para um diretório temporário e o apaga
   (`updater.rs:1217-1300` do plugin 2.10.1).
2. **O Windows não tem pacote portátil.** O instalador grava por cima de
   Program Files e não aceita outra pasta.

**Decidido (D-linha-1): publicar uma 0.15.2 que é só a linha legada
empacotada para o launcher.** Ela é a 0.15.1 com duas mudanças: esconde o botão
de atualizar quando quem a abriu foi o launcher, e sai também como pacote
portátil para o Windows. Sai com `--latest=false`, para nunca virar o `latest`
do GitHub. Senão, quem ainda está na 0.15.1 receberia a 0.15.2 pelo
atualizador, e o launcher leria o manifesto do release errado.

**Mac Intel e Linux ficam sem linha legada**, porque a linha 0.15 nunca teve
pacote para eles.

### O que a atualização para a 0.16 precisa fazer na primeira abertura

1. **Copiar os dados da 0.15 antes de qualquer outra coisa.** A cópia vai para
   `dados/servidor-0.15`, sem `lancador/` e com um marcador de pronta. Só depois
   a 0.16 migra a pasta dela. Hoje a 0.16 abriria `~/.config/seele` (no Windows,
   `%APPDATA%\tech.datadev.seele`) e migraria o banco direto, porque o
   `migrate()` não recusa um banco do futuro
   (`crates/seele-server/src/persistence/mod.rs:274-302`).
2. **Baixar a linha legada para o depósito.** O atualizador já apagou a 0.15.1
   instalada, então ela vem do release: a 0.15.2 da recomendação acima, ou a
   0.15.1 publicada e assinada.

**A cópia leva a identidade junto**, então a pessoa é a mesma nas duas linhas.
A sala pessoal pede mais do que isso: uma identidade por máquina, e não uma
cópia por linha (o ADR a escrever, «A identidade é uma por máquina»). Com
cópias, uma linha aberta antes da cópia ganha uma chave nova, e a pessoa aparece
como outra nos servidores dela.

### O manifesto

Hoje o `latest.json` descreve uma versão só, sem `schema`, `sha256`,
`executable` nem `unit`. Por isso o `Deposito::instalar` recusa toda instalação
com `ExecutavelNaoDeclarado` (`crates/seele-lancador/src/deposito.rs:276-279`),
e o «GUARDAR A MAIS NOVA» nunca instalou nada em máquina nenhuma.

**O formato da 0.16 é híbrido:**
- o topo continua no formato do Tauri (`version`, `notes`, `pub_date`,
  `platforms`), apontando para o app mais novo da linha mais nova. O
  atualizador da 0.15.1 ignora chaves a mais e exige `url` e `signature` em todo
  alvo do topo (`updater.rs:1388-1398`);
- ao lado, `schema: 2` e `versions[]`, com cada app, a linha de servidor dele,
  as APIs de MOD que ele roda, `sha256` e `executable`;
- **o `schema` nunca sobe**, porque a 0.15.1 recusaria um 3;
- o manifesto é **acumulado**: o `empacotar/manifesto.py` lê o anterior e
  acrescenta, em vez de escrever do zero (`manifesto.py:64-118`);
- um teste lê o arquivo gerado com o `RemoteRelease` do próprio plugin.

Uma correção no documento de contrato: o executável do Mac é
`SEELE.app/Contents/MacOS/seele-app`, e não o `…/SEELE` de
`docs/versoes-lado-a-lado.md:253`. Isso foi medido no `.app` da 0.15.1.

### O que muda no papel

- **O ADR 0046 ganha uma emenda.** «Cliente, servidor, protocolo e API de MOD
  sobem juntos com o mesmo número» passa a ser «a versão do servidor sobe junto
  com o protocolo e a API de MODs; o app tem número próprio». «Toda versão para
  sempre» passa a ser «toda linha para sempre». As versões 0.11 a 0.14 saem. O
  estado dele passa de «proposto» a «aceito».
- **O ADR «1.x nunca quebra o fio»** é escrito, com a linha em
  `specs/10-convencoes.md:55-57`.
- **O segundo endereço do atualizador** (`DATA-AND-DEV/SEELE`, parado na 0.10.0)
  sai na 0.16.

### F1 — O protocolo da 1.0 (Planos 2 e 3)

**O que existe:** o `Hello` leva um `version: u8` só (`control.rs:1029-1055`).
Uma variante desconhecida vira `Malformed` (`control.rs:2335`). Um `Hello` fora
da janela vira `ProtocolViolation` (`session.rs:467-471`), e o `Incompatible` de
`session.rs:488-491` nunca é alcançado. O guarda dos ordinais passa sem medir
nada, porque `PUBLICADA = 3` (`control.rs:3064-3076`).

**O S2.** Hoje o cliente assina o nonce cru que receber
(`crates/seele-core/src/client.rs:1958-1975`), e não existe
`export_keying_material` em lugar nenhum dos crates. Enquanto o app só tem uma
vaga, o acoplamento entre conectar e hospedar é a mitigação por acidente:
quando o cliente está em M, o servidor do dono está fora do ar. **O Plano 2
desfaz isso, então o S2 tem de entrar antes dele.** O portão é um teste com
três partes (o servidor X do dono, o servidor M malicioso e o cliente), verde
hoje e vermelho com o S2.

**A forma do S2 (decisão D-fio-3).** A spec de 23/09 assina o exportador do TLS
(`2026-09-23-sala-pessoal-por-codigo-design.md:213-233`). O ADR 0057 propõe
`contexto ‖ fp ‖ nonce` (`0057:551-563`), porque a WebTransport não entrega o
exportador à página. Isso não foi medido.

**Recomendação:** uma fórmula só nos dois transportes:
`rótulo ‖ fp do servidor ‖ nonce de 32 bytes`. Ela derruba o repasse: o cliente
assina a impressão de quem ele de fato conferiu, e X recusa uma assinatura com
a impressão de M. Ela também cabe no navegador. Dois rótulos diferentes
entrariam como dois contratos na mesma 0.16.

A mesma chave Ed25519 assina também o certificado da sala e o `MORO2` do ENC/2.
As três assinaturas usam rótulos distintos, num helper único.

**O Plano 2** desfaz as três respostas a «estou no meu servidor?»:
`hospedado_aqui` (`main.rs:1476`), `estado_da_porta().hospedando`
(`tela-sessao.js:3521`) e `nossoServidorEm` (`tela-boot.js:101`). Ele leva o
`disconnect` a desmontar só o cliente, cria o `parar_de_hospedar(qual)` e o
VOLTAR AO MEU SERVIDOR, e faz a saída do app encerrar as duas hospedagens.

**Uma janela de segurança que existe hoje.** `Hospedagem::iniciar` abre o laço
de aceitação (`crates/seele-server/src/hospedagem.rs:127`). Só **depois** o
`main.rs` semeia a portaria e admite o dono (`main.rs:1767-1795`). Num banco
novo, nesse intervalo, a primeira conta que chegar vira Comandante
(`permissions.rs:229`). O conserto (semear antes de aceitar) entra no Plano 2,
para as duas hospedagens. **Decidir se ele também merece uma 0.15.x** é do dono
(ver §6).

### F2 — ENC/2 (Plano 4)

- **O ponto fala as versões 1 e 2 ao mesmo tempo:** a magia separa as duas
  (`seele-proto/src/encontro.rs:153`). Quem está na 0.15 não muda nada.
- **Um conflito que a spec não discute:** todo datagrama do ENC/1 tem 96 bytes,
  de propósito, para o ponto não virar amplificador (`encontro.rs:155-162`). O
  ponto lê num balde de 96 bytes (`crates/seele-encontro/src/lib.rs:283`). A
  spec fala em «até 512 bytes».
- **Recomendação técnica:** a regra «resposta ≤ pedido», com enchimento; chave
  e assinatura em base64url dentro do texto.
- **A VPS vai antes do app**, e antes da validação de campo. O precedente é ruim:
  o ADR 0047 registra 10 dias de recurso morto por um binário velho na VPS. A
  proposta é um portão no molde do G1, «o ponto em produção responde
  `MORO2`/`QUEM2`», conferido antes do `publicar.sh`.
- **O limite por /32 corta quem divide IP de CGNAT**, e o Mac do dono está atrás
  de um. Os valores do limite e do teto são decisão do dono.
- **Um registro calado por relógio torto** (o carimbo tem tolerância de ±300 s)
  precisa ser dito pelo produto.

### F3 — A API 6 de MODs (Plano 6)

**O mecanismo:** cada região vira uma linha de `PONTOS_DE_CONTRIBUICAO`
(`mods-contribuicoes.js:76-88`), de `CONTEINERES_DOS_PONTOS`
(`camada-mods.js:1044`) e de `NOMES_DOS_PONTOS` (`camada-mods.js:832`). Os
guardas de `frontend.rs` já cobram toda linha nova. As regiões da spec
(`redes`, `servidor.navegacao`, `operador.barra`, `canal.cabecalho`,
`conversa.mensagem`, `compositor`, `pessoas.lista`, `status.barra`) estão
decididas. Os nomes ainda não estão congelados.

**O banner.** O modelo é o `pessoa.avatar`: `substituir`, por pessoa, com
`conteudo.doServidor` (`mods-contribuicoes.js:165-171`), carregado por
`avatarContribuido` (`base.js:1179`) e aplicado por `vestirAvatar`
(`tela-sessao.js:4509`). O GIF já é aceito (`mods-regiao.js:358`). Faltam três
aplicadores: o fundo do cartão da chamada (`pintarCartao`,
`tela-chamada.js:452`), o fundo de `.operador` (`index.html:1064`) e o
cabeçalho do perfil.

**O nome do banner é `pessoa.capa` (decisão D-api-1).** O nome da spec de 23/09,
`pessoa.faixa`, colide com três coisas no código:
- `pessoa.faixa` **já é** a faixa de sincronia no roster
  (`tela-sessao.js:1799`, `:2198`);
- `data-faixa` é a mesma faixa no cartão da chamada (`tela-chamada.js:454`);
- «faixa» também nomeia o toque e o veredito.

«Banner» colide com `#banner`, o alerta do produto (`index.html:631`).

**Toda região diz o que faz no celular.** Com os MODs rodando no celular
(D-web-1), o `v6.json` precisa dizer, para cada região e camada, se ela existe
na casca de uma mão, com que tamanho, e o que acontece com uma contribuição
para uma região que o celular não tem. Isso entra no contrato antes do
congelamento, junto com os requisitos das sessões de MOD.

**As camadas:**
- `chamada.palco` vira um ponto de perfil `superficie` sobre `#chamada-grade`
  (`index.html:1407`);
- a `folha` é nova, parente do `painel`;
- o `dialogo` ganha a validação declarada e os botões que o produto monta.

**Os eventos da tela** não existem: hoje o MOD lê o snapshot inteiro do produto
(`base.js:2126-2133`), inclusive o `link_state`, que traz o veredito de conexão
segura, e esse veredito é do núcleo. A API 6 entrega um **retrato projetado por
lista branca** e eventos.

**O que sai do código com a API-6-só:**
- `APIS_ACEITAS` passa a `[6]` e `MOD_API_MINIMA` a 6 (`mods.rs:77`, `:80`);
- saem os braços 3, 4 e 5 de `capacidades_da_api` (`mods.rs:88-113`) e de
  `CAPACIDADES_POR_API` (`base.js:1983-1990`);
- o teste `um_pacote_da_api_anterior_continua_carregando` (`mods.rs:785`) vira
  «as APIs 3, 4 e 5 são recusadas com `ApiTooOld`»;
- a frase de API velha (`camada-mods.js:1673-1685`) passa a apontar o Servidor
  0.15 no launcher.

**Ficam:** os `api/v1-v5.json` publicados e o guarda que os congela, o
`check-api`, e o `ultimaQueEsteBuildEntende` (`camada-mods.js:1878`), que é o que
faz a 0.16 escolher no catálogo a versão de cada MOD feita para a API 6.

**A medição de custo** do ADR 0052 nunca foi feita. Só existe
`o_custo_de_zero_uma_e_tres_instancias` (`executor.rs:3598`), que mede o QuickJS e
só imprime. **Ela não segura a construção da API 6, mas segura o
congelamento**, porque os limites de cada região congelam junto com o
`v6.json`. Mede-se a v0.15.1 agora, como «antes», e de novo com as regiões da 6.

**O `api/v6.json` e as constantes sobem por último**, quando a API 6 estiver
pronta para sair: a partir daí ela está congelada, mesmo antes da release
(`api/README.md`).

**As sessões de MOD** (PERFIS, MESA e ESTILO) estão na etapa 1: revisão e
requisitos, em `docs/revisao-0.16.md` de cada repositório. Os requisitos delas
entram no rascunho do `v6.json` antes do congelamento. A etapa 2 é o porte.

### F4 — O web app do celular (ADR 0057)

**O que está provado** (`spikes/voz-no-navegador/README.md`): num iPhone com iOS
27.0.1, numa aba do Safari em Wi-Fi:
- o WebTransport abre em 27–142 ms;
- o hash adulterado é recusado 3 vezes em 3;
- o Opus por WebCodecs passa sem perdas;
- com a tela bloqueada, o iPhone ouviu por 128 s num teste e falou por 40 s
  ou mais noutro.

**O que não está provado:**
- o certificado curto **com a mesma chave** do longo (o spike usa chave
  própria);
- o Ed25519 do WebCrypto (não há artefato em `spikes/`);
- o web app instalado, em 4G, com a página vinda de uma origem pública, no
  Android e contra o `seeled` de produto.

**As seis medições do ADR** (`0057:813-826`) vêm antes do código delas. A 1 (a
assinatura do Safari no `verify`) e a 2 (o `seele-proto` em `wasm32`) dá para
fazer no Mac. A 3 a 6 pedem o iPhone, o Android e uma origem pública, e são do
dono.

**O `seeled`:**
- o ALPN `h3` no mesmo socket, com um resolvedor de certificado pelo ALPN (hoje
  o certificado e o ALPN são únicos: `tls.rs:114`, `:118`);
- a sessão sobre dois transportes. É o maior pedaço: `session.rs` fala `quinn`
  em 35 lugares;
- os certificados curtos, com a mesma chave P-256, pré-gerados em janelas,
  guardados no banco e herdados junto com a identidade.

**O cliente:** a casca `apps/seele-app/ui/` com uma ponte no lugar de
`window.__TAURI__` (`base.js:36-37`). A `ui/` chama 154 comandos `invoke`. A
ponte implementa um subconjunto, e os outros voltam com recusa nomeada. Para
isso, um crate `crates/seele-web` em `wasm`, com o codec do `seele-proto` e o
produtor do `Snapshot` (o `state.rs` é extraível). A casca de uma mão sai da
etiqueta `arquivo/mobile-ios`, por merge com conflitos.

**A página fala só o Servidor 1.0.** Um servidor 0.15 não tem `h3` nem
certificado curto, e o link dele não traz `wh=`. A página reconhece isso no link
e diz, sem discar.

**Os MODs rodam no celular (decisão D-web-1).** O ADR 0057 recusava o celular
num servidor com MOD ligado. O dono decidiu o contrário: o celular roda os MODs.
É a maior parte nova do web app, e muda três coisas.

**1. Onde o código do MOD roda no navegador.** O desktop já teve essa
discussão. O executor de MODs saiu de um Worker de `blob:` para o QuickJS
nativo (`apps/seele-app/src/executor.rs:1-35`), porque um MOD num Worker gravou
em IndexedDB uma marca que sobreviveu ao reinício do app. No celular é pior:
a identidade da pessoa (a `CryptoKey`) mora no armazenamento da origem da
página. **Um MOD não pode rodar com acesso a essa origem.** Há duas
candidatas, e quem decide é um spike:
- **o QuickJS compilado para `wasm`, num Worker.** É o mesmo motor e o mesmo
  prelúdio do desktop, então o MOD vê a mesma API nos dois. O custo é compilar
  C para `wasm` e carregar o motor na página;
- **um `iframe` com `sandbox` e origem opaca**, com uma CSP sem rede. O
  armazenamento lança erro numa origem opaca. É mais barato, mas é um segundo
  executor, com semântica própria.

Os critérios do spike:
- nenhum armazenamento que sobreviva à sessão;
- nenhuma rede;
- nenhum acesso à origem da página;
- a mesma API que o desktop;
- o custo medido num iPhone.

**O spike escolheu as duas juntas (AB)** (`spikes/mods-no-navegador/README.md`,
no branch `0.16/web`): o motor do desktop (o `rquickjs` 0.12.2 em
`wasm32-wasip1`, com o prelúdio extraído do `executor.rs`) num Worker criado
de dentro de um `iframe` de origem opaca.

- **A (o motor num Worker) e AB passaram nos cinco critérios**, no Chromium 151
  e no Safari do Simulador:
  - nenhuma canária de rede tocou;
  - nada sobreviveu ao reinício;
  - a chave da página ficou fora de alcance;
  - a API do desktop bateu em tudo;
  - o laço sem fim é cortado em 500 ms, com a página travando 13 ms no pior
    caso.
- **AB custa de 10 a 30 ms a mais na subida que A**, e põe mais uma parede: o
  Worker mora numa origem opaca.
- **B (o `iframe` sozinho) reprovou:**
  - 8 pacotes STUN saem por cima da CSP em cada navegador, porque o
    `webrtc 'block'` é ignorado pelos dois;
  - o laço trava a página por 3 s;
  - a memória não tem teto.
- **O custo:**
  - o motor tem 942 KB (361 KB com gzip);
  - um MOD sobe em 14 a 59 ms;
  - o motor é de 5 a 7 vezes mais lento que o JIT, mas a ida e volta entre a
    página e o MOD fica abaixo de 1 ms.

  **Falta medir no iPhone**, com o dono.

**Duas condições para o produto, achadas no spike:**
- **O teto de memória.** No `wasm32-wasip1`, ele não existe com o alocador
  padrão do QuickJS: um MOD alocou 128 MiB com teto de 8 MiB. Com o
  `RustAllocator`, ele para no teto. O executor web usa o `RustAllocator`, com
  guarda.
- **A cadeia de build.** O `build.rs` do `rquickjs-sys` baixa o wasi-sdk
  (462 MB) sem conferir checksum. O `xtask` passa `WASI_SDK` e confere o SHA-256
  antes de usar. Sem isso, o build do web app depende de um download não
  conferido.

**2. A API 6 diz o que cada região faz no celular** (F3, acima). Como o motor é
o mesmo do desktop, a API 6 não pode prometer nada que dependa de o código do
MOD rodar fora de uma chamada do anfitrião. O prelúdio pressupõe isso.

**3. A medição de custo da API 6 inclui o celular:** memória e tempo de quadro
num iPhone, com os três MODs oficiais ligados.

O item 16 do contrato de fio (a recusa própria do `h3` num servidor com MOD)
sai. O ADR 0057 ganha uma emenda.

**O celular não liga pelo código na 0.16.** O navegador não abre UDP e perde o
quarto (`0057:694-704`), e o certificado Ed25519 de validade fixa da sala não
serve para `serverCertificateHashes`. Isso vai escrito nas notas.

**As razões novas de `DisconnectReason` entram uma vez só**, numa lista
ordenada a partir do ordinal 18: `ChamadaEncerrada`, `NinguemAtendeu`,
`ChamadaRecusada` e a da API de MOD que o cliente não roda.

**A linha do servidor não vira razão no fio.** Entre linhas, o par não chega a
ler o corpo do `Disconnecting`: o `decode` recusa o carimbo antes. A 0.15
responde `[8, 11, 9]`, e uma 1.x diante de uma 2.0 só sabe mandar o congelado
`[c, 11, 0]`. Dentro da mesma linha nunca há recusa por linha. Então a linha
viaja por um mecanismo só, **o byte 0**. O cliente monta um erro tipado (a
outra linha, com o número do par) a partir de
`ControlError::UnsupportedVersion { found }`, e o launcher mapeia o número para a
linha pelo manifesto (`linha_do_protocolo`).

### As decisões técnicas, com a recomendação

Estas eu sigo como está escrito, salvo objeção do dono.

- **D-fio-1 (como 1.x vira bytes):** o número que viaja continua crescendo, e a
  linha é derivada por tabela (§1).
- **D-fio-2 (a mensagem desconhecida):** ignorar e contar **na lista de
  mensagens de cima**. O quadro tem prefixo de 4 bytes e é lido inteiro
  (`crates/seele-core/src/frame.rs:14-28`), então pular um não desalinha a
  leitura. Nos enums aninhados (a razão de um `Disconnecting`, por exemplo),
  vale a regra de hoje: a variante nova só sai para quem a entende, traduzida
  pela versão do par (`session.rs:1212-1219`). Ignorar um `Disconnecting` com
  razão desconhecida calaria o fim da sessão.
- **D-fio-3 (o S2):** uma fórmula só, `rótulo ‖ fp ‖ nonce`, nos dois
  transportes (§2, F1).
- **D-fio-4 (o FORA DO AR):**
  - a lista de membros vai em partes no começo da sessão, com acréscimos para
    membro novo, banido e renomeado;
  - todos veem, sem papéis e sem horário;
  - a sala pessoal não manda.
- **D-fio-5 (a voz):** um número próprio, como a tela já tem (`screen.rs:78`), em
  vez de reescrever o byte para cada destinatário.
- **D-fio-6 (os extras do Plano 3):** mensagens novas podem chegar numa 1.1 sem
  quebrar nada, então `EditMessage`, `UnbanPerson`/`SetRole` e a confirmação de
  entrada **ficam para depois**. **Campo novo numa mensagem que já existe não
  pode chegar depois**, porque o `postcard` lê campos por posição. Por isso o
  campo reservado para E2EE entra agora.
- **D-fio-7 (a API de MOD no fio):** `ModAnunciado` ganha `api`, e o `Hello`
  leva as APIs que o cliente roda. Um servidor 1.1 com um MOD da API 7 recusa
  antes do convite o cliente 1.0 que não o roda, e a recusa diz «atualize o
  app».
- **Os hashes do celular:** 60 DERs passam do teto de 16 KiB por quadro
  (`control.rs:50`). Proposta: a mensagem dos hashes carrega só os hashes e as
  datas, e os DERs vão em partes.

## 4. A ordem

**A regra de integração:**
- cada frente trabalha num branch `0.16/<frente>`, num worktree próprio;
- tudo entra em `versao/0.16` por merge sem squash, depois de revisado;
- cada lote ou tarefa traz o teste que falha antes e a prova por reversão.

**A bateria inteira roda numa fila só.** Duas baterias em paralelo disputam a
porta 8384, e a `vaga` só serializa dentro de um binário
(`crates/seele-conformance/tests/vaga/mod.rs:136`). Cada frente testa o próprio
crate, e a bateria inteira roda na integração.

**O caminho crítico:**

```
decisões D-fio ─► infraestrutura do fio (itens 1–5, 7, 20) ─► numeração 1.0 e linha (22, 23)
             └─► S2 (6) ─► Plano 2 ─► sessão do Plano 3 ─► sala 4d ─► 6e ─► 7d
                                                                         └─► núcleo da API 6 ─► v6.json congelado ─► porte dos MODs ─► publicação
```

**Em paralelo ao caminho crítico:**
- F5, em seis ondas;
- F6 inteira;
- F3: a medição e o rascunho do `v6.json`, e as regiões depois do K3 e do K4;
- F4: as medições, a ponte, o analisador do link e a casca do celular. O
  servidor do F4 entra depois da sessão do Plano 3;
- F2: depois do M2, e a VPS antes do app.

**A ordem de publicação:**

0. **O indexador passa a aceitar a união das APIs das linhas que ele serve:
   `(6, 5, 4, 3)`.** Hoje ele aceita `(5, 4, 3)`
   (`SEELE-MODS-INDEXER/ferramentas/manifesto.py:43`) e recusa com

   as versões das duas linhas convivem no catálogo em qualquer ordem. O guarda

   do indexador contém as APIs de toda linha que o launcher oferece»**, e não
   igualdade com o `APIS_ACEITAS` do app (F3, no corte da API 6).
1. **A VPS com o ENC/2.** O ponto novo é compatível com a 0.15.
2. **Os pacotes dos três MODs na API 6, publicados antes do app.** O filtro do

## 5. Como a orquestração funciona

- **Esta sessão orquestra.** Ela escreve os specs de cada frente, abre as
  sessões, revisa os lotes, integra em `versao/0.16` e roda a bateria.
- **Uma sessão por frente.** Cada sessão escreve o próprio plano antes do código
  e registra o andamento em
  `docs/superpowers/sdd/2026-10-08-0.16/<frente>/progress.md`, que a orquestradora
  lê.
- **Sobem primeiro:** F5 (a onda 1), F6, e F3 e F4 na parte que não espera
  ninguém. F1 sobe quando as decisões D-fio estiverem fechadas. F7 sobe quando o
  S2 estiver em `versao/0.16`. F2 sobe depois do M2.
- **As três sessões de MOD** continuam nos repositórios delas. Elas mandam os
  requisitos e recebem o `v6.json` em rascunho para portar.
- **Nenhuma sessão faz push ou publica.** Push, publicação e VPS são atos do
  dono.
- **O que vai para um repositório público de MOD:**
  - o commit avaliado pelo indexador não leva `docs/`, porque o indexador
    publica a árvore inteira, menos `.gitattributes`, `.gitignore` e
    `.gitmodules`;
  - toda versão sai como **um commit só** sobre a versão publicada antes, para
    que o push não publique a história das revisões, com caminhos desta
    máquina e defeitos ainda abertos;
  - o código não cita commits nem branches que nunca vão ser públicos.

- **D-estilo-1:** a aparência do servidor também se edita pelo celular;
- **D-seg-1:** o conserto da janela do Comandante vai na 0.15.2, porque a linha legada vive para sempre, e na 0.16 pelo Plano 2;
- **D-api-2:** a `folha` substitui o `painel`; `regiao` e `cartoes` saem da API 6, e o `tema` fica, ampliado, pela porta do `servidor.aparencia`; um som de MOD repete com `repetir: true` no contrato;
- **D-api-3:** o retrato da API 6 leva só quem está presente, e não os membros fora do ar (acrescentá-los depois é API somada; tirá-los, impossível);
- **D-fio-8:** entram na 1.0 o aviso da metade de servidor de um MOD às janelas, os pedidos de MOD endereçados ao servidor e o tema como dado do servidor (rascunho da API 6, §14);
- **D-seg-2:** a 0.15.2 só assina desafios de exatamente 32 bytes. Achado da F7: o app 0.15 assina qualquer nonce de até 256 bytes com a mesma chave que a 0.16 usa, e um servidor 0.15 malicioso, visitado pela linha legada, poderia obter uma prova do S2 da 0.16 (89 bytes) ou o conteúdo de um `CertificateVerify` da sala (130 bytes). Todo servidor 0.15 legítimo manda 32 bytes (`NONCE_LEN`), então nada se quebra;
- **D-id-1:** a identidade da pessoa é **um arquivo só na máquina**, lido pelas duas linhas. A 0.15.2 passa a ler `$SEELE_IDENTIDADE`, que o launcher indica, e as cópias da chave acabam. O `$SEELE_HOME` continua como está, para os testes terem duas pessoas numa máquina (ADR 0017). Registrado no ADR 0061, da F7;
- **D-enc-1:** o limite do ENC/2 é um balde de 64 pedidos que enche a 8/s, por /32 e por /64, só na versão 2 (a 0.15 não muda), com teto de 16 384 marcas no quarto assinado. Cada app aberto manda 2 registros a cada 15 s, então cabem 60 SEELE abertos atrás de um mesmo IP de CGNAT. Quem passa ouve «RECUSA taxa», e o log diz que o limite é por endereço público;
- **D-enc-2:** o `publicar.sh` da 0.16 confere que o ponto em produção fala o ENC/2 e trava a publicação se não falar;
- **D-enc-3:** um teto de 128 marcas vivas por prefixo dentro do quarto assinado. Achado da revisão independente da F2: com o limite só por velocidade, de 4 a 7 IPv4 comuns enchiam as 16 384 vagas para sempre;
- **D-enc-4:** um cookie de ida e volta no `MORO2` (um HMAC do IP e de uma janela de 2 minutos, devolvido num `DESAFIO` sem estado). É a única defesa contra quem forja a origem, que podia encher o quarto ou calar a sala de alguém pelo IP dela. Muda o fio do ENC/2, e entra antes de a VPS ir ao ar;
- **D-api-4:** ao hospedar o Servidor 1.0 com um MOD habilitado de API abaixo da 6, o app não sobe o servidor calado: diz qual MOD e qual API, e oferece três saídas — atualizar o MOD (primeiro, quando o catálogo tiver a versão da API 6), hospedar o Servidor 0.15 pelo launcher, ou desligar o MOD e hospedar sem ele (os dados ficam, ADR 0045). A recusa `ModsDeOutraApi` antes do convite (P7c da F1) entra junto com o corte da API 6;
- **D-mods-1:** os três MODs oficiais portados para a API 6 saem como **4.0.0** (PERFIS, MESA e ESTILO). As duas linhas convivem no catálogo: a 3.x é a do Servidor 0.15 (que ainda pode ganhar consertos, como a 3.3.2), e a 4.x a do Servidor 1.0. Uma 3.4.0 na API 6 se leria como a próxima da mesma linha. A «PERFIS 3.4.0» da spec de 23/09 e do índice da 1.0 passa a ser a 4.0.0;
- **D-api-5:** um tema por servidor, o escolhido por quem administra (como já se escolhe quem desenha cada parte da tela). Cada pessoa ainda pode preferir o visual padrão do SEELE na própria máquina, pela porta `servidor.aparencia`;
- **D-api-6:** o teto de contribuições muda de modelo antes do congelamento: os pontos por pessoa deixam de contar no agregado (um por pessoa e por MOD, até um teto por ponto), e o agregado fica para os pontos sem alvo. Achado do PERFIS: com 128 no agregado e cartão, foto e capa por pessoa, cabiam só 42 pessoas numa sala de até 250. Os números saem da M3 com a API 6;
- **D-linha-2 (09/10, revê a D-linha-1):** a 0.15.2 sai **agora, como atualização normal para todos** (é o `latest` até a 0.16), e não só para o launcher junto com a 0.16. O motivo é o terceiro conserto de segurança, o da sala cheia: ele vale para quem hospeda na 0.15.1, toda vez que uma sala chega ao limite. Os MODs legados (MESA 3.1.1, ESTILO 3.1.1, PERFIS 3.3.1) saem junto; o indexador já aceita as APIs 4 e 5. A 0.16, quando sair, recebe o manifesto da 0.15.2 como o anterior. O resto da D-linha-1 vale: a 0.15.2 esconde o atualizador quando o launcher a abre, e sai portátil no Windows;
- **D-legado-1:** os consertos dos MODs no código 3.x saem para a linha legada junto com a 0.15.2: MESA 3.1.1, ESTILO 3.1.1 e PERFIS 3.3.1;
- **D-api-1:** o ponto do banner se chama `pessoa.capa`;
- **D-linha-1:** a linha legada sai numa 0.15.2 só para o launcher;
- **D-52:** o áudio abre só ao entrar numa sala de voz.
- **D-celular-1 (09/10):** a tela do celular é **um desenho novo**, feito para uma mão, com a mesma tipografia, as mesmas cores e a mesma marca do desktop, e paridade com ele dentro do escopo do ADR 0057. Não é o desktop encolhido nem o merge da `celular.css` de `arquivo/mobile-ios`. Abre a frente F8, que assume a Tarefa 3.5 do plano da F4 («a casca de uma mão»), com o guarda do contraste do MUDO e do SAIR. A lógica não se duplica: o celular muda a apresentação e a navegação, e o estado, os `invoke` e as frases ficam nos módulos de hoje.
- **D-celular-2 (09/10):** o celular **assiste à tela compartilhada na 0.16, com som**. Assistir é consumo, dentro do escopo do ADR 0057; compartilhar a própria tela continua fora. Vêm junto o som da tela na mistura da voz (com SILENCIAR, VOLUME e a fila por tela do ADR 0054), o leitor do fluxo da tela no `wasm` e a reconexão no meio de uma transmissão. Se o H.264 do iPhone não decodificar (medida do dono), o cartão da transmissão diz «esta tela não abre neste aparelho», e o resto da sessão segue;
- **D-web-3 (09/10, do dono):** **o web app também serve no PC, com a casca de desktop**, para quem entra sem instalar e não vai hospedar. Duas cascas no navegador: `data-casca="celular"` (`pointer: coarse` ou menos de 900 px na carga) e `data-casca="larga"` (a `ui/` de desktop de hoje, adaptada ao navegador), com a escolha à mão guardada no aparelho. No PC o escopo é **tudo menos hospedar**: fica de fora o que só existe para quem hospeda, ligar pelo código (sem UDP) e as versões; entram moderar e compartilhar a tela pelo `getDisplayMedia`, com medida. Revê o que a orquestradora tinha decidido antes (o notebook com a casca do celular numa coluna). O link para baixar o app é `https://seele.app.br/#baixar`;
- **D-fio-9 (09/10):** o `MAX_QUADRO_LEN` da tela congela em **4 MiB**, e não nos 512 KiB de hoje. O teto entra no fio da 1.x, que não quebra, e o maior quadro legítimo é o I420 cru de 1080p (3037,5 KiB), a maior resolução do codec. A medida da F4 (`94d4dfd8`, `F4/medidas/idr-no-teto.md`) mostra quadros acima de 512 KiB a partir de 12,4 Mbps, que o lado que envia hoje descarta. Um guarda confere o teto contra o I420 da maior resolução, calculado das constantes do `seele-video`. O enquadramento da tela vai para o `seele_proto::screen`, desenhado pela F4 e aprovado pela F1;
- **D-linha-3 (09/10):** dois defeitos de leitura da v0.15.1 publicada entram na 0.15.2, que ainda não saiu, e na 0.16. (1) Com um tema claro que a validação aceita, montado no editor do ESTILO, a conversa saía a 1,09:1 e o SAIR DA SALA a 1,04:1: o `body` resolvia a cor com o token da raiz, e o tema o redefine em `#tela-sessao`. Os três temas prontos do ESTILO 3.1.0 são escuros e não eram atingidos. O conserto é `#tela-sessao { color: var(--seele-osso) }`. A conferência de texto sobre painel fica só na 0.16 (a 17e da F3). (2) A escolha entre transmissões dizia «VER —» em todo botão, porque o palco lia `snapshot.roster`, que o `Snapshot` nunca teve; passa a ler os `presentes`;
- **D-sala-1 (09/10, pela recomendação, até o dono rever):** a sala sobe sempre na 8385. O app conta com a regra do firewall que o instalador do Windows cria e, na primeira abertura que não a tiver (o pacote portátil, ou uma regra apagada), pergunta explicando para que serve a porta: receber quem liga pelo código. Sem a regra, a sala continua no ar pela rede de casa e diz que de fora não chega;
- **D-celular-3 (10/10, pela recomendação da F8):** no celular, **o `aperto` da `#tela-auth` não aparece quando o veredito é o da impressão conferida**. A «ENTRAR EM» já mostrou o endereço e a impressão inteira, e foi lá que a pessoa tocou ENTRAR, antes de conectar. O navegador só conecta com o certificado que o link anuncia. Passar pelo `aperto` seria pedir para entrar duas vezes, o mesmo pedágio que não decide nada e que o desktop já tirou de quem hospeda. Pula-se a tela, mas não o passo: a entrada na sessão (`inserirPlug`) roda igual, e uma falha dela tem tela e frase. Continuam com tela própria, numa coluna: um veredito diferente (chave trocada, primeiro contato sem impressão) e a `espera` da portaria (`AdmissionPending`, ADR 0030). O desktop e a casca larga não mudam. A outra saída, redesenhar o `aperto` para 390 px e passar por ele sempre, fica descartada;

- **D-web-2 (15/10, do dono):** a origem do web app é **`https://web.seele.app.br`**. É permanente: as identidades do celular e do navegador moram nela, e trocá-la depois perde todas. O host precisa deixar definir cabeçalhos e não pode pôr o beacon do Cloudflare;

## 7. Riscos

- **O tamanho.** Os documentos estimam de 4 a 6 semanas para a sala, e o
  levantamento de 08/10 conclui que isso é **o piso, e não o centro**. Some 2 a 4
  semanas para a Parte II, e 4 a 6 para o servidor e o protocolo do web app,
  com o cliente web à parte. Em paralelo, o caminho crítico é o da sala.
- **Tudo espera o mais lento.** Com um pacote só, a API 6 congela no fim, e os
  MODs só são portados depois disso.
- **A válvula, se for preciso:** o protocolo da sala já entra no contrato de
  fio. Se a sala atrasar, a 0.16 pode sair sem a tela de ligar, e ela chega
  numa 1.x sem quebrar nada. **Não é o decidido**: é a saída que o contrato deixa
  aberta.
- **Os MODs no celular aumentam o web app**, que já era a frente G a GG: um
  executor novo no navegador, a casca de uma mão com regiões, e a medição num
  iPhone. Se o spike do executor falhar nos critérios de segurança, o celular
  volta a recusar servidor com MOD, e isso volta ao dono.
- **Duas instâncias abertas** (a 0.16 e a linha legada): os dois processos
  disputam a porta 8383 e o microfone. No Mac, a permissão de microfone pode
  ser pedida de novo. O armazenamento do WebView é compartilhado. **Precisa ser
  medido** na tarefa 11 da F6.

  existe:** a pasta pula de 0055 para 0057 (F3).
